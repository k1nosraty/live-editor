# Architecture

The repository and desktop product are **Live Editor**. The original brief in SPECIFICATION.md used a superseded working name. Existing application identifiers, recovery/extension storage keys and private IPC protocol keys are retained for compatibility with installed candidates; UI, executable, launcher and distribution names use Live Editor. All product code is local. Native operations are never implemented as browser simulations.

## Native boundary

The bundled main window alone receives `allow-dispatch`. The Rust gateway accepts an explicit operation name and validates every path, operation and argument. Native dialogs grant roots or individual files internally; the frontend cannot call an operation to approve arbitrary paths. Approved roots are persisted separately from frontend recovery. Blocking native work uses Tauri's blocking pool; one mutex coordinates native scope/runtime ownership.

The preview never receives the Tauri bridge or filesystem APIs. It uses a separate loopback origin and an iframe without `allow-same-origin`. Browser development uses sandboxed srcdoc. A random per-session channel validates messages against the actual iframe window. Preview messages provide console/selection information only. Source edits require a deliberate inspector UI action.

## Buffer and save model

Each document has an ID, display name, optional native path, current text, saved baseline and disk SHA-256 revision. Editing changes memory first. Disk writes compare the expected revision with disk bytes and use a synced temporary file plus replacement. A mismatch marks a conflict, preserving the editor text and the external disk content. Recovery is stored outside project sources in browser storage plus a native atomic recovery copy.

CodeMirror owns undo history for each visited document. Inspector edits activate the source editor before dispatching a source change, so they enter that document's history. Split views share buffers; each view retains its own selection/history state.

## Preview and assets

Playground HTML/CSS/JS is assembled into a fresh sandbox document. CSS-only updates replace its dedicated stylesheet without navigation; HTML/JS recreate the execution context. Static projects use an ephemeral `127.0.0.1` port and a cryptographic path token. The server serves only canonical paths under one root, rejecting hidden files and symlink escapes. Open buffer overlays replace disk bytes. Relative URLs remain relative to the original file route; CSS imports, fonts, images and ES modules are served with their MIME types. Opaque iframe module requests receive `Access-Control-Allow-Origin: null` on this read-only tokenized server. Root-relative paths and cross-root assets are current limitations.

Static CSS-only buffer updates are injected into matching stylesheets. Other source updates rebuild. Styles generated by a framework are not modified by this engine.

## Framework runtimes

Detection reads package.json and lockfiles. The first Vite start requires project execution approval, stored in native application data separately from session recovery. Approved folders start automatically on open/recovery. Execution uses an argument array, never concatenated user shell text. It uses an existing runtime/manager and fixed loopback port. An embedded Vite adapter preserves project plugins/configuration and overlays dirty editor buffers through load, HTML and hot-update hooks. Validated snapshots live in a private temporary directory, never in project sources. Changes and Undo trigger Vite HMR; closing or saving a buffer clears its overlay. The snapshot is seeded before startup to include recovery edits. Windows children are assigned to a kill-on-close job; Unix children use a process group for normal cleanup. Logs and console entries are bounded.

## Extension choice

API v1 uses validated declarative contributions rather than running third-party code. This provides themes, insertion commands, templates, text panels and read-permission document events while keeping arbitrary extension JS outside the privileged context entirely. See EXTENSIONS.md for the complete schema and permission rules.
